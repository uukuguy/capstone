# systematic-debugging

Separate a software failure, source rejection, transport uncertainty, empty result and a business observation. A business anomaly does not itself establish a defect or root cause.
Collect the exact bounded failure, relevant inputs, source/environment identity and last known successful step. Compare a working case and trace the first boundary where the observed behavior differs. Protect credentials and source records.
State one testable hypothesis and choose the smallest authorized observation that distinguishes it from alternatives. Keep successful work and record rejected explanations. Do not repeat an unchanged failed call or retry an uncertain source effect; recover its receipt and obey current returned retry restrictions.
Apply a correction supported by evidence, then check the original failure and direct consumers. Several failed corrections require reassessing assumptions and dependencies, not an expanding patch stack.
When the cause remains unknown, deliver observations, ruled-out explanations, missing evidence and a bounded next action. Use existing diagnosis records where available; keep their outcome linked to the shared task plan.

When the native skill record tool is available, load this exact admitted skill and report meaningful public phases with related tool IDs and product references. Loading does not prove application or successful verification. Use a bounded summary; never include credentials or private reasoning.
