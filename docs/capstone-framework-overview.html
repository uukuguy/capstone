01 / Ownership model

四层边界，让责任可以被解释。

Capstone 的依赖方向只有一个：应用选择组合，Domain Pack 定义领域语义，Kernel 管理中立运行，Registered Authority 产生事实。边界清晰，系统才可以替换模型、增加领域，并保留可信证据。

03 / Trust model

把“可信”变成可检查的合同。

可信不是模型语气更像专家，而是每个重要结论都有清楚的所有者、版本和运行范围。

边界提示：离线信息回答不会创建模拟证据；模拟器或 Authority 支持的结论，只能引用当前运行已准入的结果和证据。

Authority owns facts

模型不能访问 raw DataFrame、pandapowerNet、PyPSA Network、shell 或任意文件。登记的 Authority 负责计算、修订和结果集。

Current run only

答案只能使用本轮被绑定的 result/evidence 引用。历史运行不能被悄悄拼接进当前结论。

Required failures stop

必需的答案、证据或引用持久化失败时，运行会失败关闭。报告、预览和进度等诊断故障不会篡改已提交答案。

给技术团队的补充：为什么没有把 Domain Pack 直接塞进 Kernel？

Kernel 只拥有中立的组合、上下文、Turn、轨迹、工件、回放和 framework core。领域语义、工具契约、策略、指南、Authority 适配和结果投影由 Domain Pack 负责。这样新领域可以独立安装，且不会让 Kernel 依赖某个业务系统的内部对象。

05 / Release architecture

部署不是一条线，而是三个隔离阶段。

本地适合高频迭代，Cloud Development 负责远程集成验证，User Trial 只接收已验证的同一源码修订或镜像摘要。

1 / 3

环境隔离

Cloud Development 和 User Trial 不共享 PostgreSQL、工件 bucket、操作员令牌、Provider 凭据、公开 origin 或可变运行数据。

同一版本

API 与 Worker 在同一阶段必须使用相同的测试源码修订或精确镜像摘要。

可回滚

云端验证失败时回滚到最后一个已验证的 User Trial 修订，不把普通开发推送直接变成用户版本。

06 / Operator workflow

业务用户看到的是一条清楚的工作流。

App 是展示客户端。它不拿 bucket 凭据，也不直接读取原始工件；它通过相同的 `/api/v1` 合同获取有界投影。

从案例到证据：选择已登记案例，先查看完整模型图，再逐条或自动执行指令，最后在同一页面查看结果图层、报告和当前运行证据。

07 / Use it locally

从源码到本地 App，只保留一条可靠入口。

本地修改 API、Worker 或 App 后，使用仓库提供的 rebuild 入口，确保容器不会继续运行旧镜像。

当前本地 App 和 API 均可访问，健康检查返回 200。

Local quick start

首次安装或源码修改后的最短路径

# 创建忽略的本地配置，并替换示例值
cp deploy/local.env.example deploy/local.env

# 重建当前源码对应的 API、Worker 和 App
make capstone-local-rebuild

# 打开 App；API readiness 由 rebuild 校验
open http://127.0.0.1:5173/
