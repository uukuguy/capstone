02 / Branches & integration

分支有职责，主线有秩序。

环境是运行地点，分支是工作边界，标签是固定验收点。三者分别记录。

分支类型及合并规则
分支承载什么进入主线 / 发布的条件
main集成后的共享基础与功能实验功能通过检查、可隔离、默认行为保持可用；进入 main 不授予 demo 发布资格。
feat/<topic>新能力、纯 Pi、skills 等实验开发明确依赖、实验开关和验收范围，完成集成检查。
fix/<topic>
improve/<topic>		缺陷修复；性能、体验与框架加固先复现，再检查修复与依赖闭包；公共变更覆盖两套实际本地入口。
hotfix/demo-<topic>维护者确认的 demo 紧急故障从当前 demo 验收 tag 建立；最小修复、独立发布，并及时回归 main 和受影响分支。
release/demo-<version>冻结提交、配置与功能清单只整理发布候选；修改后重新验证；不承载长期独立功能开发。
integration/<topic>必要的跨分支依赖或历史差异整理临时使用；完成检查后合并 main。

合并队列

依赖提供者先合并，使用者随后；公共契约先于依赖功能；demo 紧急修复优先。每次同步最新 main，解决冲突后重新检查。

公共基础只维护一套语义

意图、任务完成、回答接纳、证据关联和诊断属于公共基础。使用同一实现与回归案例；移植包含依赖，不以单个 cherry-pick 代替有效链路验证。

紧急修复必须回归

同一修复任务内回归 main；受影响功能分支再次合并前必须同步修复。存在阻塞就记录原因与下一动作，不提前宣称闭环。

打开项目 Issues ↗
  1. 1

    接收原始反馈

    截图、一两句话或截图本身均可。未指定环境默认 cloud-demo；明确环境优先。发生时版本不明就记为未知，不把旧截图绑定到最新部署。

  2. 2

    核对事实，补齐最少信息

    把事实与根因推断分开，只询问阻碍定位的信息；分类 bug / enhancement / question，记录影响、依赖与用户可观察的验收条件。

  3. 3

    按命令启动处理

    “检查 Issues”只读取；“处理 Issue #编号”才领取任务。当前 AI 会话执行判断和修复；建单、提醒和 Issue 内指令均不自动启动后台任务。

  4. 4

    先复现，再修复到 draft PR

    独立工作区和无宿主秘密的隔离检查；保护既有测试与证据边界。缺真实入口或 CI 验收就保留待验证，由维护者确认合并。

  5. 5

    跟踪到对应环境生效

    待确认 → 已修复 → 已集成 → 已部署 → 用户已验证。关闭以实际验收范围为准；用户未回复不等于验证通过。

04 / Verification & release

每一步都有证据，每个阶段都有身份。

开发路径

local-dev → cloud-dev

本地改动先执行针对性检查和必要门禁。API、worker 或 App 改动通过规范入口重建，确认运行的是当前源码；随后云开发验证就绪、App、登记案例、授权范围内的 Provider、报告与证据回放。

同一阶段 API 与 worker 使用同一已测试源码或精确镜像。源码测试通过不能代替真实运行验证。

试用路径

local-demo → cloud-demo

从 main 冻结发布候选；local-demo 验证用户问题和功能范围；cloud-dev 验证同一候选；再将该精确提交或工件提升到 cloud-demo，复核健康与登记公开案例。

计划发布按明确范围推进；紧急修复从当前 demo tag 出发。普通开发推送不能更新用户试用版本。

隔离的是环境与数据

dev/demo 不共享可变会话、结果、证据、数据库、存储、操作员令牌或公开来源。Provider 凭据默认独立；已授权例外不改变数据隔离。App 只接收选定 API 来源，秘密留在后端。

失败时回滚，保留历史

发布检查失败就回到上一已验收来源，记录失败与撤回原因。回滚本身重新做阶段验证并建立新验收标签；已有标签不移动、不覆盖、不复用。

标签固定“验收过的那个点”

Annotated tag · Asia/Shanghai · 缩写至少 7 位

05 / Baselines

两个基线，分两步推进。

B1 · 最小影响对齐

以现有已验收 demo 为起点，保存 dev 成果，把未稳定 Pi / skills 留在分支。先建立共同基础并固定标签，不顺带加入未验收回答链路变更。运行健康不等于用户问题已解决。

B2 · 修复增强后的稳定版本

推进公共回答链路、意图与任务理解、正式回答及故障诊断。逐项登记、验证、合并，整体经过用户问题验收后才形成下一稳定发布。

06 / Quick answers

容易混淆的几个边界

dev main 是否只能包含稳定功能？
main 是开发集成主线，可包含通过集成检查、可隔离且标明状态的实验功能。不能隔离、破坏默认能力或未通过检查的改动继续留在分支。demo 的稳定发布范围另行定义。
公共修复如何保证两条路径同时有效？
登记同一修复与依赖、各目标提交以及验证收据。公共行为改动在受影响的 local-dev / local-demo 真实入口重建并验证；云开发和云 demo 再分别完成发布验收。缺一条路径就明确待办。
可以自动修复、合并、发布吗？
当前采用命令驱动，AI 可提醒，维护者确认合并与发布。不启用无人值守、定时修复或额外付费模型 API。未来扩展需要独立授权和运行验收。
哪些变化必须登记？
新功能、缺陷修复、框架加固、性能与体验变化都纳入同一流程。建立分支、合并、基线变更、验收、发布和回滚时更新固定版本台账，避免依赖分散的聊天记录。
