# Capstone v1.1.0 — unified framework baseline

Status: release candidate. Full local and dual-platform release verification,
main PR acceptance and the annotated `v1.1.0` tag are pending. A tag will be
published only after the accepted release source is known. This is a source
baseline release; it does not update cloud-dev, cloud-demo or local-demo.

## Included scope

- Application → Domain Pack → Kernel → registered Authority ownership. The
  independently installable pandapower application owns its workers, entry points,
  reports and trajectory projections. The Kernel stays domain-neutral.
- Native Pi conversation and enterprise execution, admitted tool discovery,
  bounded independent tool composition, continuation, saved products and restore.
- Durable resource uploads, incremental projections, bounded attachment access
  and version-bound references. Storage quotas remain separate from processing
  and model-context limits; enterprise scale gates remain separately documented.
- State Grid PPT default, persistent scoped template library, session selection,
  immutable source bundles, rerendering and PDF from the same PPTX. Saved receipts
  bind the template, content, dependencies and renderer identity. Actual-current-call
  service-bus counters remain distinct from accumulated job counters.
- Registered pandapower/PyPSA authorities and packs, current-run result/evidence
  ownership, the shared App/API contract and isolated deployment stages.
- Development branch ownership audit and closure. Original research and superseded
  implementation heads have exact archive references, not active delivery status.

The functional baseline is dev `8d97596c` (PR104). Its local runtime acceptance
includes four real model rounds, retained State Grid selection, saved PPT/PDF,
47 matching download records and browser restore. Those checks are not a full
release receipt. See [PPT acceptance](../reports/2026-11-14-presentation-integration.md).

## Versions and compatibility

The root product metadata, `capstone-agent` distribution and operator App are
1.1.0. Independently owned Kernel, Domain Pack, Authority and professional
application versions retain their own published contracts; they are not all
renumbered to the product release.

The retired `grid-agent` distribution and CLI are absent. Use `capstone-agent`;
formal pandapower runtime belongs to `pandapower-application`. Earlier references
to its migration being pending were outdated and are corrected in both READMEs.
The prior CLI compatibility commitment had already been withdrawn. This release
number does not restore it. Authority tool/schema and result contracts keep their
existing versions. Credentials and ignored runtime directories remain private.

Existing local conversations, resources and products were preserved during the
accepted integration rebuild. This is not a guarantee that an older application
can read every newer format; rollback compatibility and deployed-stage acceptance
need their own evidence. No installer can bypass its declared data-format gate.

## Explicit limits

IG1 acceptance, later enterprise worklist items, business-analysis quality and
reference-only external-model projection research remain separately tracked.
The mature lightweight chain is reused; this baseline does not claim another DR
runtime, zero data egress, all pending research implemented, or a new grid numerical
result. A package version or a main merge does not imply cloud/demo promotion.

## Release process

1. Freeze the candidate from current dev and retain the existing main ancestry
   without rewriting history. The old main-only commit is an ancestry merge,
   with no source delta against dev.
2. Align version metadata, local dependency pins/locks and release notes. Repair
   release-gate blockers under their owning contracts; keep failed receipts.
3. Complete local `make check-release`, then obtain explicit approval for one
   main PR macOS/Linux full release gate. Do not reuse prior scoped-CI approval.
4. Merge the accepted main PR and create/push an annotated `v1.1.0` tag on its
   exact accepted source. Do not create stage-acceptance tags or deploy services.
5. Return release version/fixes to dev through its required PR process and
   refresh the actual-dev canonical control register. Every further CI needs its
   own explicit approval; no direct push to either permanent branch.
