# MCP 工具选择与业务工具组合优先：联合讨论稿

状态：供 Capstone 与 data-gateway 讨论，尚非双方确认的新接口契约。无需网关按本文直接实现全部建议。

## 要解决的问题

客户端应优先使用适用的业务工具及其合法组合；只有必要时才使用底层灵活工具。具体有哪些工具、每个工具的适用范围、限制和替代条件，应由当前网关通过 MCP 自描述。客户端不能依赖仓库文档、固定工具名称、固定工具清单或固定的三级调用流程。

“业务工具 → 结构化查询 → 原生 SQL”可描述本实例的一些选择，但不是所有 MCP 服务都必须具有的三层结构，也不是每次执行都要走的顺序。统一发布的工具可以保持同等权限地位，同时具有不同的业务用途和适用条件。

## 已知的 Capstone 缺口

原选择策略主要约束原生 SQL，未充分指导智能体区分业务工具与通用结构化查询。避免原生 SQL，并不代表使用了业务工具组合。

此外，客户端需要控制错误后的路径：参数错误先核对契约；新参数结构先验证一个有界调用；批次发生共同错误后停止扩散；超时后根据证据调整路径或选择。大量变体查询不能自动视为智能组合。无合理修正时应保留缺口并推进其它有价值工作。

这些是客户端责任，不能要求网关通过新增迎峰度夏专用接口、增加超时或替客户端兜底来解决。Capstone已补充指导草案和相关入口测试；行为效果仍需实测，不能以提示词或单元测试代替。

## 建议的职责边界

| 网关提供事实与契约 | 客户端作选择并组织执行 |
| --- | --- |
| 当前发布的能力、用途、输入输出及限制 | 根据本次问题选择适用工具及合法组合 |
| 实例实际可用范围与不可用原因 | 不把局部不可用推断为全局不可用 |
| 业务操作与灵活接口之间的适用、替代条件 | 业务组合优先，必要时有依据地使用灵活接口 |
| 输出与输入可关联的身份、版本、时间、单位条件 | 核对条件后传递结果，不靠名称相近关联 |
| 错误分类、可修正条件、相关替代能力 | 区分纠参、改路径、保留缺口与停止批次 |

权限与选择偏好分开：发布某个工具不等于要求优先调用它；工具选择指导不产生新授权。

## 可选实现路径

### 建议先做：现有 MCP 自描述补齐，加客户端通用指导

不先增加强制元数据协议。网关从现有统一契约定义生成一致的说明：

1. 握手 `instructions` 和全局发现摘要说明“适用业务工具组合优先，底层灵活工具用于必要补充”，并指出如何按需发现有关能力。
2. 相关工具说明明确它直接解决什么、不能解决什么、适用的替代条件。当前通用结构化查询的说明应与原生 SQL 的指导一致，避免智能体认为所有结构化查询都是首选业务路径。
3. 详细契约按需返回组合条件和有关替代能力，说明条件而非强制顺序。指向的工具必须属于当前实际发布范围；建议不是自动执行命令。
4. 不可用与错误结果明确作用范围。若提供后续建议，应能区分“此能力未配置”“参数可修正”“覆盖不足”“其它能力可能适用”；不能把潜在替代能力标成已经可用。

客户端读取这些已发布说明，不按具体工具名称或表名路由，不强制查遍所有能力，不新增一次独立模型评审。

### 如实测仍有歧义：再讨论可选的机器可读选择信息

可讨论“操作角色、适用条件、替代关系、限制”的结构化表达，但字段名和取值尚未约定。应来自同一契约源，与自然语言说明一致。信息应可缺省、可扩展；未知角色不能使客户端失效，也不能产生硬编码工具组排序。

不建议先规定所有工具必须属于固定三层、强制先调用某个发现接口、让客户端维护网关业务路由表，或为每次回退增加独立推理和审批。

## 需要双方确认

- 网关现有契约源和发现接口，是否已能表达上述适用条件？优先复用哪些现有字段或说明位置？
- 本地联调的运行量测、统计和气象工具哪些实际已配置？客户端应从哪个 MCP 返回中可靠获知，而非读取仓库文件？
- 通用结构化查询是否同意明确定位为业务能力之外的必要补充？哪些合理操作本来就应使用它？
- 第一轮是否只补齐现有说明和结果建议，以真实任务验证后再决定是否需要新元数据？

## 联合验收

全新会话只给连接与认证，不读仓库文档。至少覆盖：有直接业务工具、需要组合业务工具、业务未覆盖需灵活查询、局部能力未配置、参数错误、查询超时、疑似工具缺陷。

同一原则还应在工具改名、部分工具未发布或工具集变化时成立。验收应检查实际调用及选择依据、错误是否停止扩散、证据与产物是否保留，而非要求业务工具占比达到某个数字。合理回退是成功路径之一；一个示例任务完成不等于策略已经稳定。

网关诊断其内部查询计划、执行和取回；Capstone诊断模型选择、上下文、参数构造、组合和重试。用相同执行轮次与 request_id 对账，分开记录双方修正。
