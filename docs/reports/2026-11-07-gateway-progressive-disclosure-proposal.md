# 给 data-gateway：渐进式契约发现调整方案

状态：提请网关侧评审。新增协议字段和操作名均为建议，尚未实现或协商确定。
范围：网关元数据协议与 Capstone MCP 适配器。保持通用发现，不固化业务工具清单。

## 1. 目标与实测依据

目标是让客户端尽快进入任务，只向模型披露当前决策需要的信息。
不要求每个工具先读用途、再读 Schema；不要求首连下载所有工具的完整契约。

本机本轮测量：

| 项目 | 实测 | 口径 |
| --- | ---: | --- |
| 连接并准备网关发布快照 | 2.129 秒 | 适配器 prepare，一次样例 |
| 单个工具 usage | 44 毫秒、6423 字节 | 请求到返回；序列化 JSON，非网络流量 |
| 单个工具 input_schema | 42 毫秒、2541 字节 | 同上 |
| 客户端完整发布快照 | 397502 字节 | 包含所有 tools/list Schema 的内部快照 |
| 去掉初始化全量契约后的 prepare | 1.965 秒 | 同机另一次样例；不能据此证明显著提速 |

此前约 100 秒是模型发现、分析、调用工具并保存方案的整轮时间，
不是初始化。最新会话提交后 1.57 秒开始执行，3.13 秒取得首次发现结果。
这些时间不能混为一个指标，也不能把不同样例相加称为实测端到端耗时。

当前浪费有两个来源：

1. Capstone 初始化额外调用了无 tool_name 的完整契约和发现接口，仅用于
   校验发布版本。客户端候选已去掉这两次调用，仍保留版本检查。
2. 标准 tools/list 包含所有工具的 Schema。即使模型菜单按需加载，客户端
   仍全量下载、校验和保存 Schema。仅分段 describe 不能解决这一层。

因此，这轮协作重点是减少全量传输和模型重复理解，不是节省一次几十毫秒请求。

## 2. 建议接入流程

```text
initialize：声明支持的发现协议、实例身份、当前发布版本和元数据入口
  ↓
获取轻量能力目录：身份、用途摘要、前提、引用关系、版本、效果声明
  ↓
模型结合任务筛选能力；必要时展开某个工具集或翻页
  ↓
只取选中工具所需的精确契约；允许一次取多个工具、多个分段
  ↓
客户端校验 Schema、授权、版本和引用后调用
  ↓
同版本复用；发布变化后重新绑定，源端失败不使元数据失效
```

用途摘要已足够时，直接获取 input_schema。只有用途或组合约束仍不清楚时
才补 usage；只有结果解析需要时才补 output_schema。允许主动读取完整的
单工具契约，但不把完整契约作为所有任务的固定前置动作。

## 3. 网关需要支持的协议

### P0：独立的轻量目录与发现协商

建议在 initialize 的 experimental 元数据中声明一个版本化发现扩展。
声明包括实例身份、publication_revision、目录操作名、批量契约操作名和
支持的协议版本。客户端只使用服务声明的入口，不自行拼接业务工具名。

新增轻量目录操作，或给 discover_gateway 增加明确的 compact/index 视图。
扩展入口应能由 initialize 声明直接定位，使支持新协议的客户端无需先
下载完整 tools/list 才知道如何使用它。入口自身的精确输入契约须通过
版本化扩展约定或握手描述提供，不能形成“先拉全量才能发现轻量入口”的循环。

每条目录项至少提供：

- 稳定工具身份：id、registration_id、toolset_id、provider_id、可调用名称。
- 简短名称、用途、适用问题、关键前提、输入/输出引用类型、组合约束。
- 分页单位、采样单位、预算作用域；未知与截断字段保留明确标记。
- 效果声明：只读、破坏性、幂等、外部访问等，用于客户端初步准入。
- contract_revision、summary_revision，以及精确契约各分段的指纹或等价校验标识。

目录不得包含完整 input_schema/output_schema、全量枚举、长篇示例或全套指南。
目录准入只授予“发现与取得契约”的资格；执行前仍须校验选中工具的精确契约。
模型不需要理解所有工具，客户端也不应为了建立目录就取得全部精确 Schema。

工具增多时支持按工具集展开、分页及有界搜索。首次目录可先返回工具集摘要
与少量入口。分页必须绑定同一 publication_revision，提供截断/总数/下一页信息。
搜索返回候选及匹配方式，不由网关替客户端决定业务路由。

### P0：按选择批量取得契约

建议增加批量请求，或扩展现有 describe_gateway_contract：

```json
{
  "publication_revision": "opaque-publication-revision",
  "requests": [
    {
      "tool_id": "identity-returned-by-index",
      "expected_revision": "tool-contract-revision",
      "sections": ["input_schema"]
    },
    {
      "tool_id": "another-returned-identity",
      "expected_revision": "another-tool-contract-revision",
      "sections": ["usage", "input_schema"]
    }
  ]
}
```

以上为协议示意，不是现有可调用接口。实际字段与操作名由网关确认。

返回要求：

- 每项保留稳定身份、section、contract_revision、分段指纹和明确状态。
- 单项失败可定位，不得把缺失、截断或版本不符伪装成成功契约。
- 精确 Schema 必须完整。超出响应预算时明确拒绝或提供受控分段读取，
  不返回截断后仍声称完整的 Schema。
- 支持明确的批量项数/返回字节预算。先声明上限，避免客户端盲试。
- 缓存可通过已知版本/指纹得到 unchanged 响应；客户端没有对应正文时不得
  请求或接受只有 unchanged 的结果。

批量接口的作用是消除无意义往返，不意味着一次请求全部工具。
旧单工具接口和省略 section 的完整响应继续兼容。

### P0：一致性与调用边界

publication_revision 表示一个一致目录快照；contract_revision 表示工具契约；
summary_revision 只表示摘要内容。三者不可混用。

- 目录和批量契约响应应明确绑定发布版本。变更期间返回 publication_changed，
  或明确支持指定旧快照；不得把不同时刻的条目无声拼接。
- 分页 cursor 绑定发布版本，版本失效须明确报错。
- 应提供条件版本校验，以免每次连接都完整遍历两遍目录。
- 执行时应能在实际派发前校验 expected contract revision，或提供等价的原子
  版本绑定机制；版本不符时明确 executed=false。这可避免“检查后再调用”的竞态。
  适配器的本地版本检查不能代替网关派发边界的校验。
- 元数据指纹需有明确算法与规范化规则；不同传输包装不能改变契约身份。

不要求标准 tools/list 返回假 Schema 或删除现有工具。保留标准 MCP 兼容路径；
新客户端通过显式协商选择轻量扩展。旧客户端继续原路径，新客户端不会为验证
扩展又先走一次全量路径。扩展不受支持时明确降级，不静默反复重试两套协议。

### P0：总线断开时，元数据仍可用

目录、契约读取、版本检查只能依赖网关已发布的本地元数据，不能等待业务服务
连通、刷新业务目录或探测源端。首连不知道源端状态时应标为 unknown，
不能根据“契约可读”推断“源端可用”，也不能以源端不可达拒绝契约读取。

已发布契约、源端可达性、缓存业务目录新鲜度是三个独立状态。任何缓存目录都
应保留来源、时间和 source_accessed 标记，不得被当作实时业务数据。

源端失败继续沿用已发布的阶段诊断：connect/send/receive、request_sent、
result_state、automatic_retry、remote_cancellation_confirmed。保留 request_id，
让客户端判断受阻操作；不能将单个业务调用失败升级为整个网关不可用。

本机已验证：真实源端连接约 20 秒超时，明确 request_sent=false、
result_state=not_produced；失败后同一工具 input_schema 可读取，正文与
contract_revision 均与失败前一致。send/receive 的结果未知分支尚无真实故障验收。

## 4. Capstone 配套责任

- 删除初始化时全量 describe 和非必要模型发现调用；该候选已通过本地测试，
  尚未因这项改动重新部署。
- 协商新扩展后，以轻量目录建立发现视图；只在工具选中后取精确契约。
- 保留工具效果准入、Schema 校验、引用所有权和版本检查；轻量目录不绕过执行安全。
- 模型菜单只加载选中工具。摘要、精确契约、执行证据分别存储；同版本契约可复用，
  不把历史业务数据作为当前事实。
- 不强制 usage→input_schema 的固定两步。已有摘要足够则直接加载/取得精确输入契约，
  解析结果有需要才取输出契约；消除本地 load/describe 与远端 describe 的重复正文。
- 源端失败后保留元数据通路；阻止网关明确禁止的自动重放，让模型评估独立工作与受阻依赖。

## 5. 联合验收

先在“本机联调”验证，不访问 63/66。两侧固定并记录源码与发布版本。

| 场景 | 必须验证 |
| --- | --- |
| 新连接、未选工具 | 零次全量契约读取；不注入全工具 Schema；源端状态 unknown 可接受 |
| 选中一个工具 | 只传该工具需要的分段；一次请求可覆盖实际所需分段 |
| 多工具组合 | 一次有界批量取所选契约；不扩成全量预读 |
| 同版本续轮 | 复用已存正文，仅补缺失分段；不重复读全部用途 |
| 目录分页/途中发布变化 | 不混合版本；明确刷新或旧快照策略 |
| 契约变化后执行 | 派发前拒绝旧版本；明确 executed=false |
| 总线断开前后 | 首连与后续元数据均可读；业务失败不改变契约，除非确有发布更新 |
| 不支持新协议 | 明确走旧协议一次；无循环探测、无假 Schema |

分别记录：初始化/目录/契约请求数量、真实传输字节、解包正文大小、模型输入 token、
连接到目录就绪、提交到模型启动、首次有效工具调用、整轮完成时间。
若传输层只有正文大小，必须注明，不能声称网络流量下降。

固定同一模型和任务，进行多次首连与续轮对照，报告中位数和慢样例；
先比较确定性的调用数和正文，不能用单次几十毫秒差异证明用户体验改善。
实际性能目标根据本机基线协商，不在本方案中虚构已达成的 SLA。

## 6. 建议交付顺序与反馈

第一批交付：轻量目录协商、选中工具批量契约、快照/派发版本一致性，以及断线元数据测试。
复用现有 capability 与 section 数据，避免重新维护另一份业务清单。
条件未变响应、搜索和更细分页可后续优化，但首批必须有明确的目录与批量容量边界。

请网关侧反馈：扩展名称/版本、实际入口及 Schema、版本与指纹语义、分页/批量上限、
旧客户端兼容方式、派发前版本校验方式，以及“本机联调”的更新版本和验收样例。
Capstone 在这些契约确认后接入，不按工具数量或业务工具名称识别新能力。
