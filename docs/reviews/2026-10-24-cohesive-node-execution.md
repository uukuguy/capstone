# 连续执行意图：实现与验证

2026-10-24。来源：`fix/workspace-reading-type` 的未提交工作区，基础提交15980389。
设计依据：[31轮调用研究](2026-10-24-report-call-granularity.md)。
用户已同意按判断边界组织程序，并允许结合研究中有明确价值的部分。

## 已实现

- 原生只读产物句柄保留相同授权、版本、路径和生产者验证，同时携带可读文件名、
  按名称识别的媒体类型、大小、哈希、角色和输出槽。节点赋值投影保留这些元数据，
  不把它们当成分析质量或内容正确性的证明。兼容缺少可选元数据的旧句柄。
- 报告渲染器读取来源失败时，直接返回`source_missing/source_unavailable`、
  相对文件名和section/block字段位置。错误留在stderr，成功stdout收据保持原契约；
  不输出实际宿主路径，不自动改名、补文件或重试。
- 原生任务执行指导明确区分数据依赖与推理依赖：输入和方法已知后，
  一段程序可读取数据、生成代码、执行、处理结果并保存输出。
  有依赖的操作在程序内顺序完成；独立工具仍可在同一模型响应中批量调用。
  新信息改变方法、需要解释的选择和未知错误仍回模型；不要求提前规划未知工作。
- 合成任务按文件类型和槽位选择所需图表/文档，不逆向检查每个复现脚本。
  不增加逐行动LLM审查、质量拒绝、自动重做、固定调用轮数或全局可写上下文。

没有更换Pi、引入第二调度器或托管执行服务，也没有为专业Domain Pack开放shell。
本次未改变UI；原有工具开始/结束、活动计时、结果与取消路径继续使用。
脚本内部细步骤不是独立的模型工具调用，不把工具计数降低当作工作量消失。

仅为交给另一执行器而创建中间文件，不构成独立任务结果。不同分析结果、授权边界、
