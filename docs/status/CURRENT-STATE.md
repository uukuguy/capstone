## Current Architecture

- CLI contracts: explicit v1.0.1 compatibility commands (`run`, `analysis`, `report`) write exactly one two-field JSON answer envelope to stdout, including validation failures for unsafe externally supplied question IDs; `analysis-generic` writes the validated composite `core` + `domains.<binding_id>` result. Progress, validation detail, and diagnostics stay on stderr without a raw traceback.
- Package assembly: the repository has thirteen Python distributions and two Pi npm packages, including the neutral `capstone-agent` host and `pypsa-agent` application. Grid/reference and PyPSA installs use separate Python environments because their pinned simulator dependencies require incompatible pandas major versions.
- PyPSA model library: the authority registers 15 project models and the six pinned PyPSA 1.3.0 `pypsa.examples` Networks. Official NetCDF assets install with size/SHA-256 verification into ignored runtime storage or the backend image at build time; current-run model revisions bind the source digest. The application-owned case catalog identifies runnable regional stress, SciGRID-DE dispatch, and AC/DC topology workflows separately from catalog-only studies. Local scripted-agent output is a bounded presentation with admitted results and evidence.
- Unified session host: `capstone-agent` uses one persistent, sequenced worker protocol for headless, interactive, and loopback HTTP/SSE modes. Registered pandapower and PyPSA workers run in separate pinned environments; both have provider-free scripted demos and Provider route assembly. Registered Provider cases inject bounded current-step context through the Kernel without exposing future instructions or expected answers. Terminal runs show timed, bounded progress and a final report path; captured stdout remains one composite JSON result. HTTP exposes ordered turns, SSE replay, final result, and authority-verified current-run evidence. Post-change local Provider execution has completed the pandapower task and the PyPSA SciGRID-DE case. The older `tools/capstone_client.py` command remains compatible.
- Hosted operator path: PostgreSQL owns durable sessions, idempotent creation and commands, sequenced events and worker leases; private S3/GCS storage holds reports and bounded admitted evidence projections. One backend image runs API or worker on local Compose, Cloud Run, or Railway. A worker releases a ready session after a configurable ten-minute idle interval; when capacity is full and a new session waits, the shared ledger atomically reserves the globally longest idle session after a 30-second grace period. Active turns and report generation are excluded, and committed answers remain available. Per-worker capacity defaults to eight and can be tuned while additional worker replicas scale total capacity. The independent Vite App targets the same `/api/v1` contract locally and on Vercel. Opt-in public demo mode issues a distinct server-derived credential restricted to scripted cases; the App obtains it on each load and enters automatically, without a login form or credential persistence. A tab stores opaque run IDs and creation keys so refresh restores each case's last run without opening another session; the automatic submission loop itself does not restart on refresh. Local Compose and browser acceptance completed both registered application types for three turns, report and evidence. The current Railway API and Worker deployments are healthy and use the same source contract as local Compose.
- Development and release lanes: local Compose plus Vite is the high-frequency loop; isolated cloud development validates remote API, worker, Provider, App, report, and evidence behavior; the isolated user-trial stage receives only the exact verified source revision or backend image digest. Cross-stage databases, buckets, credentials, origins, and mutable run data remain separate. Normative boundaries are in `docs/architecture/capstone-development-lifecycle.md`, with Railway operations in `deploy/railway/README.md`.
- Operator network workspace: the light App opens each case's complete authority-backed model diagram before a run, then replaces it with current-run step layers. The API prewarms registered case diagrams in its own process and serves them through an authenticated, bounded endpoint; no preview creates run evidence. The first manual click starts the session and submits instruction 1; ordered automatic execution waits for each committed step's network outcome before advancing, with a bounded fallback if that optional view does not arrive. Per-case latest-session retention, completed-step selection, task focus, and a completed-run reset to the initial manual/automatic choice remain available. A generated power-science AI illustration introduces the framework; completed reports appear beneath the central analysis timeline. Registered grid/PyPSA authorities supply complete, persistent current-run diagrams and step layers through sequenced events and authenticated replay; the Kernel stays domain-neutral. SciGRID-DE uses all 585 buses, 852 lines, and 96 transformers with model geographic coordinates; IEEE-39 uses all 39 buses, 35 lines, and 11 transformers with model schematic coordinates. Schematic buses use busbars, geographic buses use location points, and diagram zoom requires Shift with the wheel. The desktop presentation restores centered outer margins and compact typography at browser 100% zoom. Numeric coloring is restricted to admitted per-element results for the matching authority revision; the highest returned line loading is deepest red on an explicitly relative scale, with partial coverage and unavailable states explicit.
- Domain runtime profile seam: CLI selects `pandapower_domain.build_pandapower_profile()`, then `capability_agent.prepare_domain_runtime(...)` materializes contracts, `environment.describe`, the tool catalog, guide index, current-run authority, executor, and projector registry.
- Generic application seam: `ApplicationProfile -> AgentApplication -> DomainBinding -> Domain Pack`; one application may explicitly select several independent bindings. The Kernel owns the framework `core` output section and each Domain Pack owns `domains.<binding_id>`. Per-binding preparation, tool routing, authority, credentials, evidence, and answer admission remain isolated. An explicit application-owned `ReferenceGrant` permits a verified, read-only opaque reference handoff for one source, target, kind, purpose and capability family; other cross-binding sharing remains denied. `analysis-generic` emits `capability-agent-output/1.0`; explicit `run`/`analysis`/`report` compatibility adapters retain the exact v1.0.1 `question_id`/`answer_output` stdout.
- Single-run compatibility: online and simulator-backed `run` use the generic controller and read committed answer text bound to the current-run event, path, hash and schema; missing/corrupt evaluation sidecars do not veto it. Application-owned physical snapshots expose legacy root events/tool-results/evidence without becoming authority inputs. Deterministic offline information returns before workspace creation. Safe provider/start and waiting events feed stderr progress through one runtime setup path.
- Agent Kernel: `capability-agent-kernel` owns neutral domain interfaces, runtime composition, tool catalog/guide materialization, trajectory primitives, artifacts, replay, and compatibility exports consumed by `grid-agent`.
