# Capstone 会话连续性与按请求加载上下文

状态：用户已批准共享会话与两阶段方案，并确认独立意图识别节点。
首个节点实现使用 Pi 驱动的大模型；后续可以使用 Jev 或专用小模型。
运行时已在本地实现并接入；真实模型的意图准确率与回答表现尚待验收。
实现与验证范围见[本地记录](../../reviews/2026-10-08-intent-context-local-verification.md)。
归属：[普通回答主线](../plans/2026-10-07-capstone-conversation-completion.md)。

## 1. 已确认的要求

所有指令都由底层 Pi 处理。进入 Pi 不代表普通问答已接通。
应用必须理解本次请求，再选择所需的上下文和能力。

普通问答与业务工作共享会话连续性。用户可以临时处理无关日常事项，
也可以用天气等外部信息补充业务讨论。不能用两套互不相通的历史实现分类。
工具不能仅按“普通／业务”划分：同一个查询工具可能服务两种用途。

稳定行为配置遵守 Pi 的配置组织和加载机制，不由 Python 代码拼接固定角色。
用户明确排除关键词自动分类。关键词、正则和固定句式不能作为意图路由，
也不能在语义理解失败时兜底。确定性的协议和权限校验不属于意图分类。
业务模型、计算约束、Authority 和证据仍遵守现有所有权契约。
顺序为：完成并验收 Capstone 普通回答，再比较纯 Pi，最后设计 skills/MCP
等能力的安装配置。本设计不提前安装新闻、天气或其他 MCP 服务。

- 新闻请求 `attempt_7014a444a41a69bb` 被识别为 `ordinary`，Pi 返回了截图中的回答。
  它使用 pandapower profile，最终没有结果或证据引用。

- `thread_application.py` 在运行会话之前获取业务 capability Context。

- `thread_service.py` 的前文选择限于当前 ModelContext 的最近一次终态请求。

  用显式系统提示词文件及允许的扩展启动 Pi。这是当前受控运行的事实，不能
  简单删除这些开关以开放宿主机器资源。

## 3. Pi 机制与使用边界

依据仓库 [Pi 锁文件](../../../configs/runtime/pi-runtime.lock.json) 对应源码，
核对了资源加载、扩展事件和会话格式。以下是机制，不是 Capstone 已实现的功能：

- Pi 支持 `SYSTEM.md` 和 `APPEND_SYSTEM.md`；项目文件的发现受项目信任设置影响，
  显式来源与默认发现有优先级，不能自行假定所有同名文件都会叠加。
- Pi 有原生会话消息与会话文件。扩展可在 `context` 事件修改发送给模型的消息副本，
  在 `before_agent_start` 调整当前请求的上下文；扩展也能控制活动工具。
- CAPSTONE 可利用这些公开机制实现自己的消息投影和能力边界，无需改 Pi 内部实现。

固定源码参考：[ResourceLoader](https://github.com/earendil-works/pi/blob/b79e4cc834970cca69daebffab7df1da7d1e52c4/packages/coding-agent/src/core/resource-loader.ts)、
[扩展契约](https://github.com/earendil-works/pi/blob/b79e4cc834970cca69daebffab7df1da7d1e52c4/packages/coding-agent/docs/extensions.md)、
[会话格式](https://github.com/earendil-works/pi/blob/b79e4cc834970cca69daebffab7df1da7d1e52c4/packages/coding-agent/docs/session-format.md)。

## 4. 上下文由三部分构成

| 部分 | 内容与用途 | 使用规则 |
| --- | --- | --- |
| 共享会话 | 用户和助手可见消息、明确偏好、任务线索、当前操作对象的简短标识 | 理解前文；不自动变成执行指令或事实证据 |
| 本次请求 | 目标、指代对象、与前文的关联、缺失条件、需要的信息或操作 | 决定回答、查询、解释、计算或澄清；允许组合 |
| 执行资源 | 当前实际可用工具、相关指南、模型约束、准入结果和外部来源 | 仅为本次请求加载；受注册、权限、选择和证据规则约束 |

共享历史可跨普通与业务请求，也可跨模型切换保留。每条相关历史带 Turn、
模型上下文和完成状态，以便区分“刚才那个模型”与当前模型。
没有可靠地区资料时，不从测试网络名称猜测真实地理位置。

“用户之前说过”“助手之前回答过”“外部来源提供”“Authority 已验证”是不同
来源。翻译或概括旧文本可直接使用历史；重新断言具体计算事实时需要绑定有效证据。
普通问答引用一段业务历史，不因此自动获得业务执行权限。

## 5. 请求理解方案比较

| 方案 | 优点 | 代价与风险 |
| --- | --- | --- |
| 扩充关键词分类，切换两份提示词（已排除） | 无 | 用户明确不接受；不能可靠识别指代和混合任务 |
| 同一 Pi 先理解请求，再由应用准备资源后执行 | 先形成可审计决策，再加载业务资源；适合现有 Python 网关和 RPC | 增加一次有界模型准备阶段及延迟 |
| Pi 单次循环内发现并动态激活能力 | 接近连续交互，可按需扩展 | 当前动态注册、准备和证据准入尚未贯通，容易提前扩张到 CONV-05 |

用户已批准第二种，保留原生能力发现的后续演进位置。两阶段属于同一个
Thread/Turn/Attempt，不创建新的用户可见会话，也不另接一个分类服务。
首版准备阶段使用同一已配置 Pi/Provider；不依赖当前关闭的 Jev 路由。
两阶段之间的契约属于应用，不属于 Pi。后续替换意图节点引擎不改变执行阶段。

### 5.1 独立意图识别节点

节点对外接口为 `recognize(IntentRequest, NodeControl) -> IntentDecision`。
实现身份另存 `IntentEngineIdentity`，含引擎、模型、配置版本及契约版本。
不以 `JevDecisionRouter` 命名通用接口，也不把 Pi 特有事件泄漏到节点输出。

`IntentRequest` 包括当前 Thread/Turn/Attempt 身份、用户原文、固定历史截止点、
带来源的共享消息、当前对象的简短身份、实际可用能力目录和用户显式模式提示。
目录中的能力需区分已注册、已启用和当前可用；描述可发现性不等于执行授权。
不传入 Provider 凭据、Authority 内部对象或原始业务数据。

`IntentDecision` 包括请求目标、关联类型、引用消息/对象身份、所需操作和能力、
缺失条件及澄清问题。每个子目标都有独立资源需求，不用单一业务标签覆盖混合请求。
引用身份必须来自输入，能力需求必须可解析到输入目录。未知能力用缺失需求表达，
不能伪造已注册能力身份。模型置信度即使存在也不授予权限。

节点调用允许产生三类结果：有效决策、需要用户澄清的有效决策、运行错误。
`NodeControl` 提供截止时间、取消检查和 lease 心跳；引擎实现必须遵守同一契约。
超时、格式错误、非法引用和缺失引擎均明确失败；不执行关键词兜底。

应用验证后把决策交给上下文准备节点。后者负责按注册表、当前选择和权限获取
必要资源，最终才进入 Pi 执行及 Domain Pack/Authority 准入。意图识别节点不能
修改模型、启用工具或持久化计算结果。Jev/小模型替换时必须通过同一组场景和
结构契约测试；测试替换不自动启用生产运行或影子调用。

```text
固定会话输入
  → 意图识别节点（首版 Pi；后续可替换）
  → 决策校验
  → 上下文与能力准备
  → Pi 执行
  → 应用 / Domain Pack 准入
```

准备阶段加载基础 Pi 配置、共享会话投影、用户原文和有界能力目录，尚不加载
领域角色与模型执行规则。Pi 给出结构化的请求决策。应用验证决策后准备所需
资源，再交给 Pi 完成回答。结构化输出只是意图建议，不是权限授予。
实施前需用 loopback Provider 验证固定 Pi 版本的结构化结束与第二阶段启动。

建议决策包含：

- 当前目标，可包含多个顺序子目标；
- 与前文关系：独立、延续、补充或尚不明确；
- 所引用的消息身份和对象身份，必须存在于输入投影；
- 所需操作类型：直接回答、改写、目录查询、外部查询、读取业务结果、计算；
- 候选能力身份及缺失条件，只能引用实际输入目录中的身份。

`ordinary/professional` 可保留为兼容展示，但不再决定整套上下文。
显式普通/业务发送可作为用户意图提示，不能覆盖能力检查或使缺失事实变成已知。
注册 scripted Case 使用既有确定性执行计划，不再进行自由意图分类。

准备阶段每个 Attempt 至多一次；输出非法或失败时给出可恢复错误，不回退到
关键词、正则分类或“带全部电网上下文的普通回答”。语义歧义应产生面向用户的
澄清请求；模型或配置故障应报告执行失败，不能伪装为用户表达不清。
取消和 lease 检查覆盖两个阶段。
不持久化隐式推理过程，只保存验证后的决策、引用身份、配置版本和执行状态。
真实额外模型费用与延迟必须在验收记录中列出。

### 5.2 意图记录与执行投影

用户批准继续修正通用边界，拒绝逐问题调整提示词。当前实现把完整
`IntentDecision` 传给普通及业务执行；其中模型生成的说明可能复述无关目录，
因此仅筛选工具与对象不足以保证上下文边界。

应用增加共同的 `capstone-execution-plan/1` 投影。执行目标只包含目标身份、
操作类型、用户原文任务片段、消息/对象/能力引用、依赖和结构化阻塞状态。
原文片段必须是当前用户指令的非空原样子串；原生 Pi 决策工具要求每个目标
提供 `instruction_excerpt`。兼容旧的注入式决策时缺省为完整用户指令，不猜测
子任务。执行仍得到原始指令与同一共享历史，不用任务片段取代用户原文。

`description`、`missing_requirements` 的解释文字和 `clarification` 问句只用于
意图记录与诊断，不进入执行上下文。应用按已经验证的结构产生
`unresolved_requirement`、`clarification_required`、`dependency_not_ready` 状态，
不按文字关键词重分类。执行模型结合用户原文、历史和实际资源解释缺口或
提出问题。状态不授予工具权限；业务仍按既有 Domain Pack/Authority 准入。
原生节点要求布尔型 `clarification_required` 控制是否需要澄清，不用说明
字符串控制执行。旧的注入式节点缺少该字段时保留旧契约兼容语义。

普通和业务路径调用同一个投影函数。投影版本与实现进入配置身份，防止旧
Attempt 悄悄换用新语义。目录仅在目录目标需要时提供；结果仍是冻结的检索
候选，不能把历史事实提升为当前证据。

验收采用通用场景矩阵与非干扰检查：改变意图说明措辞不改变执行输入；
改变用户任务、历史、依赖或已授权资源时，相关输入必须变化。矩阵覆盖
日常操作、文本改写、专业概念、业务读取/执行、缺失外部来源、混合依赖、
澄清和模型切换。loopback 只证明输入与流程；真实模型表现另行验收。

## 6. 配置组织

建议在 `configs/runtime/capstone-pi/` 保存版本化的基础 Pi 配置：

```text
configs/runtime/capstone-pi/
  SYSTEM.md                 # 应用身份、会话与来源规则
  APPEND_SYSTEM.md           # 可选应用补充规则
  settings.json             # 允许的 Pi 设置，无凭据
```

该路径已在本地实现。基础配置由 Pi 原生加载器读取，不把普通/业务分支写成 Python
字符串。阶段工作目录和 agentDir 由应用明确控制，使用受控配置来源；不借此
自动读取开发仓库 AGENTS.md、开发者 HOME 或未注册扩展。Provider 凭据仍使用
现有受保护配置，不能复制进这些版本化文件。

业务策略和指南继续归 Domain Pack 所有，由应用选择后通过受信 Pi 扩展按次
加载；不复制成全局电网角色。天气或检索能力未来有自己的注册说明，不塞进
pandapower 包。普通回答同样可以使用已注册、已授权的通用能力。

历史、当前任务和外部观察进入消息上下文，而非被提升为 SYSTEM.md 内容。
配置加载清单记录来源、版本和摘要，便于解释一次回答使用了哪些资源。
配置缺失或不兼容需明确失败，不用另一套写死的提示词偷偷替代。

## 7. 会话保存与恢复

Thread ledger 保持唯一的业务持久化来源。Pi 会话文件是 Attempt 执行记录，
不另立一套可独立修改的业务状态。切换话题不会清空 Thread 或创建两个互斥历史。

应用从已提交的用户/助手消息构造有界历史投影，包含普通与业务消息；历史按时间
排列，引用的必要旧消息另行补入。预算使用配置项并记录截断，不静默假定丢失
内容。首版不增加另一套模型摘要服务。未完成的助手片段只提供中断状态，不作为
完成结论；重试避免重复当前用户消息。

受信 Pi 扩展通过原生消息/context 机制加载该投影。不能伪造 toolResult 来模拟
历史证据，也不能把旧结果 handle 当成本次已准入结果。准备与执行共享同一固定
历史投影，执行阶段再加入已验证的资源资料，避免两次模型调用看到不同会话。

保存 Attempt 的历史截止 event_seq、选中消息身份、配置摘要和决策。重试及恢复
按原始快照运行，不自动换成更新的模型、工具或配置；旧快照所需资源不可用时
给出明确恢复错误。结果仍按现有当前运行准入规则处理。

## 8. 场景及验收

| 场景 | 预期上下文和行为 |
| --- | --- |
| 电网分析中问“今天的国际要闻” | 理解是独立新闻请求；有检索能力则使用，无则说明缺口；不推销电网任务 |
| 问“明天北京天气” | 查询明确地点和日期；不自动把天气归入电网计算 |
| 问“这个电网所在地的天气” | 引用会话中可靠地区信息；缺失或存在多个地点时澄清 |
| 问“这种天气影响刚才判断吗” | 关联天气和此前判断；区分概念解释与需要重新计算的结论 |
| 问“把刚才的结论翻译成英文” | 使用所指历史文本；不重复计算；不提高旧结论的可信等级 |
| 问“为什么会这样” | 结合最近对话解析指代；仍有多个合理目标时澄清 |
| 闲聊后说“继续刚才的 N-1” | 找回相关业务任务和模型身份，检查选择与能力，再读取或执行 |
| 换模型后问“与刚才那个相比” | 区分两组模型身份与结果，遵守已有跨上下文证据规则 |
| “查天气并按它重新计算” | 分解查询和业务输入；没有可靠映射、输入或工具时明确缺口，不擅改模型 |
| 工具全部关闭仍讨论专业概念 | 正常解释；只有需要工具的具体事实或执行步骤受到限制 |

检查分三层：

1. 可重复契约测试：带不同历史的相同指令，得到不同关联；准备结果校验、缺失
   能力、历史来源、跨模型指代、取消、重试和配置版本固定。
2. 实际 Pi RPC + loopback 捕获：验证原生配置加载、消息角色、两阶段执行、
   普通问题不带电网执行策略，业务请求仍保留准入机制。天气使用明确 fixture，
   不能据此宣称已有线上天气能力。
3. 授权后的真实 Provider/App 验收：记录原始问题、回答、加载资源、工具调用、
   时间和费用。评估直接性、连续性、缺口说明和业务事实正确性。

只有第三层经用户体验确认，才能称普通回答已接通并推进纯 Pi 对照。
本轮研究没有调用真实 Provider，也没有部署。

## 9. 代码落点与范围

- `turn_router.py`：以 Pi 语义理解和决策校验替换 `_heuristic_route`；移除关键词
  兜底。审计目录问句检测和后处理中的固定句式推断，避免换一个入口继续做意图分类。
- `thread_service.py`：提供有界 Thread 消息投影及来源身份，内存/PostgreSQL 一致。
- `thread_application.py`：理解请求后获取必要的业务资源，保留原始模型和工具选择。
- `kernel_pi_session.py` 与受信应用扩展：对接 Pi 配置和消息上下文，不拼接历史系统指令。
- Kernel 运行启动器：只提供中性的受控加载参数；普通/业务策略仍归应用与 Domain Pack。

本设计不重构纯 Pi 参考模式、不安装 skills/MCP、不升级 Pi、不改模型转换或
多 Run 协议。动态能力安装配置保留到用户指定的后续阶段。
