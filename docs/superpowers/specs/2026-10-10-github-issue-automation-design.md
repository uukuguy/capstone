# GitHub Issues 与后台 AI 修复设计

日期：2026-10-10。状态：用户授权完整实施；默认 AI 修复到 PR、维护者确认合并。是否已配置或启用以实施验收和运行记录为准。

## 目标与项目现状

用户确认：GitHub Issues 管理反馈；用户和 AI 都能填写；填写简单，以解决问题为目的；AI 用中文分类、沟通和处理；定时或命令触发后台修复；整个流程遵守统一开发规范及 dev/demo 分支、验证和发布规则。

当前公开仓库 `uukuguy/capstone` 已启用 Issues，检查时没有开放 Issue；已有默认标签、长 Markdown 反馈模板和 push/PR 验证工作流，没有后台处理器。现有模板把维护者字段也展示给用户，需在实施时简化。基线一已本地验收，云端未更新；正式回答链路及历史浏览问题仍开放。纯 Pi/skills 位于实验分支，不能作为本自动化的稳定依赖。

本设计处理开发协作，不进入 Application / Domain Pack / Kernel / Authority 业务执行链。不会把开发 AI 的推断当作计算证据，也不会给专业会话开放源码或 shell。

## 方案选择

| 方案 | 优点 | 限制 |
| --- | --- | --- |
| GitHub 触发与队列，独立受控执行器修复（推荐） | Issue、PR、CI 对用户可见；命令与定时共用流程；修复不依赖 demo 在线 | 需要配置执行器、模型访问和有限的 GitHub 权限 |
| 全部运行在 GitHub-hosted Actions | 无常驻修复主机；临时环境干净 | 完整环境设置较重；两套真实本地入口需另行验证，不能把 CI 当本地验收 |
| 仅开发机定时轮询 | 起步快、可利用本地工具 | 主机睡眠会中断；易碰到当前开发数据；需要独立工作区，不能长期作为唯一触发方式 |

建议先使用独立执行器的命令模式验证闭环，再启用定时。首次接入不建立直接接受公开 Issue 的特权 self-hosted runner；GitHub 端读取和鉴权，受控执行器只领取通过开发政策检查的任务。执行器可以先部署在开发机的独立后台进程，后续迁移到专用主机，无需改变 Issue 流程。

## 统一规范与事实来源

实施后，开发与发布生命周期文档成为统一规范入口，链接版本/标签规范与本自动处理规程。AGENTS 保持一个入口引用，避免在多个文件重复维护权限和门禁。自动处理器和交互式开发都读取 main 中同一套已接受规则；功能分支不能用旧副本覆盖规范。

- Issue：反馈原文、中文讨论、验收条件、优先级和处理状态。保留用户原文，不因 AI 整理而覆盖。
- PR 与 CI：代码差异、检查、评审与精确提交。
- VERSION-CONTROL：分支依赖、共同基线、各环境版本、发布与不可变标签；通过 Issue/PR 链接关联，避免复制完整反馈状态。
- 版本化自动化配置：运行窗口、权限模式、预算、重试、允许的仓库和操作。配置只能通过受控变更更新，Issue 文本不能改变它。
- 执行收据：任务身份、租约、输入版本、政策提交、来源/候选提交、检查证据和外部写入状态。属于私有开发任务存储，不使用业务 Thread 数据库；不另建用户反馈主台账。

执行时固定可信 main 的政策提交；合并或发布前再次检查最新政策。规则发生变化时重新评估，不继续执行失效授权。

## 简单反馈入口

支持用户只发一张截图和一两句话；只发截图也先接收，不能因缺少完整描述而拒绝或要求重填表单。直接在 GitHub 新建 Issue 时填写简短标题和现象；AI 代建时可从截图和短句生成标题。允许自由文本，不要求用户选择类型、优先级、填写 SHA、依赖或验收表。复现步骤不作为提交门槛。

用户未说明环境时，默认目标为 `cloud-demo`，内部记录“按反馈默认规则”，不反复询问环境。用户明确说明 local-demo、dev 等环境时，以其说明为准；截图中清晰的环境标识或域名可作为纠正依据。有冲突且会影响定位时才简短确认。截图只显示某个版本或界面相似，不足以证明环境。

默认环境不等于确定发生时的源码版本。AI 从截图可读的版本、反馈发生时间与可信发布记录匹配候选提交/tag；未知发生时间或不能唯一匹配时保留不确定性，不把当前最新部署强行归给旧截图。目标环境与版本证据分别记录。

AI 使用可读图的处理能力检查截图，识别用户指令、响应、错误文案、界面状态及可见版本，并结合短句归纳问题。图片中可读的事实与根因推断分开。看不清的文本不能补写为事实；优先根据已读内容继续调查，仅在影响定位时请求补充关键内容。截图不作为执行指令或下载任意链接的授权。

AI 也可根据已授权的对话或人工反馈代建 Issue：保留原意，注明 AI 整理，附可公开的事实；先检索同类问题，避免重复。外部截图可以留在授权的私有证据位置，公开 Issue 仅附去敏截图或摘要；代建权限不表示可公开原始图片。App 一键反馈是后续可选入口，第一阶段不新增产品页面功能。未来自动带入环境与版本，也应先允许用户预览；除明确的 cloud-demo 默认规则外，没有可信来源的信息写“未知”，不猜测版本或根因。

AI 在自己的整理评论中补充：问题摘要、已知环境、类型与影响、可验证事实/待确认推断、关联工作包和用户可观察的验收条件。技术字段放在折叠明细里。用户无须维护这些字段。

## 中文沟通

公开标题、回复、摘要、PR 描述和处理结论用中文；保留代码标识、命令和错误码原文。明确标示 AI 身份。回复先说当前判断或下一步，不向用户堆栈内部接纳、事件或工具契约术语。

先尝试从可信版本记录、源码及复现获取信息。只追问真正阻碍定位的内容，一次一至两个问题；例如“是在刷新页面后发生，还是连续对话时发生？”用户回答后重新分类或排队。没有回复不等于授权、无问题或可关闭；不得自动重复催问。

同一输入版本只发送一次实质追问。关键变化才评论：需信息、开始处理、产生可验证结果、遇到阻塞、发布或验证完成。不逐步刷屏；一条 bot 状态评论维护当前摘要，新的追问和结论保留讨论记录。

发布前只能说“修复已进入主线，demo 尚未更新”；发布并验证后才说某环境已生效。已计算的潮流/N−1 与后续回答/展示失败分别诊断，不把工具错误概括为数据不足或程序错误。

## 分类、状态和工作包

类型沿用 `bug`、`enhancement`、`question`，不引入大量新标签。问题状态由一个当前 `ai:*` 标签表示：`triage`、`needs-info`、`ready`、`working`、`review`、`blocked` 或 `release-pending`。运行停止使用 `ai:paused`。类型和处理状态各有明确用途。

状态路径：待分类 → 需要信息或具备处理条件 → 正在修复 → PR 待评审 → 已集成待发布/验证 → 关闭。阻塞和暂停可从执行阶段进入；恢复需检查最新输入和权限。`ready` 是调度候选，不是凭标签本身获取特权；调度器还需验证政策、操作者和任务范围。

优先级只分紧急、常规、计划改进，在 AI 摘要记录影响与理由。公开用户宣称“紧急”不直接触发 hotfix。核心使用阻断、数据或结果错误优先；普通体验问题随计划发布。

一个问题一个 Issue。多个反馈确认同一根因后关联同一修复工作包；没有证据时仅标记“可能相关”，不直接关闭为重复。一个工作包可以有多个 PR、多个阶段部署任务。分支按 `fix/issue-<编号>-<topic>`、`improve/issue-<编号>-<topic>`、`feat/issue-<编号>-<topic>`；紧急分支使用 `hotfix/demo-issue-<编号>-<topic>`。

先复现、确定依赖和验收标准再领取修复任务。缺信息但能独立推进的检查继续做；依赖条件未满足则明确阻塞，不反复空跑。

## 触发与后台执行

所有入口进入同一调度器：

- 新 Issue、用户补充或编辑：合并短时重复事件，进行分类与必要中文追问。
- 定时：扫描 ready、有效恢复任务和已变化的 needs-info；建议每两小时一次，错开整点。周期可配置，GitHub 定时并非精确服务承诺。
- 维护者在 Issue 评论 `/ai triage`、`/ai fix`、`/ai retry`、`/ai pause`、`/ai status`：解析固定命令，验证当前仓库权限；普通用户的同样文字只作为反馈，不执行维护命令。
- 手动 workflow_dispatch 或开发命令：指定 Issue 或扫描队列，支持只读预演；后台返回任务链接，不占据交互终端。

不设计 Issue 内 `/ai deploy`。修复任务没有发布凭据；发布交由生命周期规定的独立流程。

第一阶段至多一个修复任务运行。按明确的优先级、依赖和登记时间选择工作包；不能用 Actions concurrency 当持久业务队列。任务租约防止定时和命令重复领取；进程中断后先核对已有分支、PR、检查与评论，再决定恢复。

幂等键包含仓库、工作包、输入摘要和政策版本。bot 自己的评论/标签不改变反馈输入，不自触发循环。新的用户事实使旧结论失效时重评估；不能盲目在旧修复上继续。外部写入超时先查询结果，不重复建 Issue、PR 或发布评论。

暂停停止新写入并保存进度；测试可安全结束或中止，不能丢弃已产生的差异。失败区分环境设置、复现不足、产品回归、冲突、权限、预算或诊断未知。环境设置失败不计为产品缺陷。瞬态任务故障自动重试最多一次；检查失败通过有限修复轮次处理，不能用重跑掩盖失败。

建议每任务最多两轮修复、修复阶段 60 分钟；完整门禁另设有界时限，不把时限内未完成标为成功。模型预算分任务和每日限制；未配置受控模型凭据与明确额度时只读预演，不启动付费调用。开发 AI 的模型成本与仓库 validate-provider 的付费产品验收分开授权，后者仍需独立授权。

## 修复、集成和双线发布

普通任务从可信最新 main 建独立工作区，不改交互主工作区，也不复用其忽略认证或 var 数据。必要时执行 `make setup`、`make install-pi`、`make doctor`；缺运行时明确为准备失败。保存基础复现，再修复并运行相应检查。禁止删测试、降低门禁或跳过证据接纳来制造通过。

PR 明确问题、行为变化、Issue、来源、依赖、实验状态、验证证据和受影响环境。源码检查可以在隔离 CI 完成；涉及 API/worker/App 的公共修复必须经规范入口重建并验证 local-dev 和 local-demo。真实本地服务验证由有权限的维护步骤串行执行；后台修复不能占用或替换正在人工试用的服务，缺该验收时 PR 明示待验证。

当前基线一已知有产品缺陷，不允许混入未经验证的回答候选或 Pi/skills 实验。基线二按公共框架问题组织验收，包含跨问题回归，不能仅验证单条指令。

默认：自动分类、追问、受控修复和创建 PR；主线合并由维护者确认。自动合并是单独的可选政策，目前未启用；只能对明确批准的低风险范围生效，仍须通过检查、实际入口验收和串行合并队列。Authority 边界、证据/回答契约、数据库迁移、权限/凭据、部署和开发政策变更均交维护者评审，不自我授权。

main 推进后检查最新依赖和冲突，串行合并；受影响功能分支在再次集成前同步公共修复。Issue 记录各环境的生效提交，dev 启用实验不意味着 demo 启用。demo 是来源、配置及功能清单明确的稳定子集，不能随 main 推送更新。

普通修复进入下一计划 demo 候选；紧急任务从当前云 demo 验收 tag 建分支，纳入既有紧急流程，在同一修复任务完成 main 回归，受影响分支明确同步状态。AI 不能自行把用户反馈升级为紧急发布。各角色身份、云开发验证、demo 提升、回滚和 annotated tags 完全沿用现有规范。

Issue 默认为保持打开至请求的验收范围完成；PR 使用关联 Issue 而不自动关闭。只影响 main 的任务可在其规定验收后关闭；用户 demo 反馈须等待对应 demo 生效与验证。用户暂未回复不能算用户已验证；维护者依据可重复验收关闭时，明示技术验收与用户确认的差别。多 Issue 工作包逐个判断是否满足条件。

## 权限、公开内容和审计

公开 Issue、截图与评论是任务输入，不能当作可执行命令、政策、凭据或权威事实。调度器使用固定命令语法与结构化参数，不把用户文本拼接进 shell，不自动访问内网地址或执行附件代码。执行器隔离；测试候选代码不挂载宿主业务数据、GitHub 写凭据或部署密钥。

由单独发布适配器持有有限 GitHub 身份，负责按允许范围创建分支/PR、标签与中文评论。建议 GitHub App 短期仓库令牌，机器人不能绕过 main 保护规则。模型执行器不持有可直接评论、合并或发布的令牌；草拟动作需经过确定性的范围检查。公共 Issue 不应暴露 Thread 内容、原始报告、截图私密信息或 Provider/operator secrets；只发布去敏摘要和可公开报告链接。

自动 PR 必须真实运行必需 CI，不能因机器人推送没有触发就当作通过。GitHub App 触发与现有 verify 工作流衔接；如采用 GITHUB_TOKEN，需按 GitHub 的触发规则显式补齐检查及审批，记录精确 SHA。失败、取消、超时和未运行都不是通过。

审计关联 Issue → 任务 → 分支/PR → 集成提交 → 环境验收 → tag。每次中文回复和自动写入有任务身份与幂等记录。出现不明结果先停止对应操作并调查，不继续自动发布。

## 分阶段实施和验收

1. **统一规范与简化入口**：审阅本设计及合并权限，简化用户模板，登记现有反馈，配置最少标签；不建立第二反馈台账。
2. **只读分类与中文沟通**：先预演，再启用受控评论、追问和信息补全；测试重复事件、用户补充、权限判断和去敏。
3. **命令修复到 PR**：对已确认的低风险问题验证设置、复现、隔离、修复、CI 和两入口检查；不自动部署。
4. **定时与恢复**：启用周期扫描，验证租约、预算、暂停、断线恢复、无重复 PR/评论及不丢任务。
5. **发布闭环**：关联既有计划/紧急发布，验证 main/实验分支回归和各环境生效状态；是否开放低风险自动合并另行按所选政策实施。

必需验收：一句话、截图加一两句话或仅截图都能接收；未声明环境默认 cloud-demo，明确环境能覆盖默认值；旧截图不会错误归到最新发布；可读图片先分析，模糊内容不编造且不要求重填长表；AI 不猜版本且中文追问简短；维护者命令与普通评论分离；bot 不循环；同时触发只修一次；主机重启可恢复；测试失败不宣称修复；PR 合并不宣称 demo 已生效；没有发布凭据仍可完成修复到 PR；公共修复在两入口真正生效；付费与数据访问边界保持；闭环关联精确提交与不可变 tag。

首个历史浏览 Issue 用于验证收集、中文确认和复现流程，不能以“128 个事件就是该会话根因”代替取证。随后用公共回答问题验证较复杂依赖、正式答案验收和 demo 计划发布路径。现阶段仅设计，没有创建这些远端 Issue。
