# Lightweight intent contract

## Routing and downstream compilation — user correction2026-10-12

Intent recognition is a light LLM classification, not a Domain Pack requirement
compiler. Its model output contains only schema and general/professional route.
The host binds that route to the unchanged original request and selected model;
no business schema, measure, ordering, capability availability or input-gap
validation belongs in this phase. Complex requests remain professional even
when their research completion is unavailable. No keyword routing is introduced.

After the route is persisted, the selected application compiles the existing
typed task proposal with published Pack contracts. The compact intent wire below
is the downstream compilation wire, not the routing output. Pack resolution,
authority execution and answer admission keep their full checks. Routing and
compilation use separate tool-free processes, timing events and failure codes.
Both reuse bounded processes with acknowledged empty sessions. Retry preserves
the original immutable route; implicit cross-turn history remains forbidden.

The user requires lightweight LLM inference for intent recognition. Each new
instruction still receives semantic inference, including bounded explicit
conversation history. No keyword route or example-specific system guidance.

The failed controlled experiment on21c02e1/off shows duplicate semantic fields
can contradict one another. A load selector can also confuse a connection point
with its attached devices. Low thinking fixes these examples but produces
thousands of reasoning tokens and violates the latency goal.

Use compact `capstone-task-intent/1` only for the model wire response. One goal
contains intent text, scope, scenario, conclusion, measure, execution,
dependencies, missing requirements and the selected Pack proposal. It does not
repeat purpose, subject, change and obligations as separate generated prose.
The host expands those textual views without changing the intent. Existing
durable `capstone-task-understanding/2` and current-run admission remain intact.

The model sees a wire schema with projected payload fields removed, and their
allowed values listed as goal fields. The host retains the complete original
schema. Flat object roots support this projection; root composition, references
and cross-field constraints fail closed rather than being silently rewritten.
Nested selector constraints remain intact. Schemas without projection stay
unchanged. Real ambiguity receives the same bounded semantic review for typed
and professional compatibility proposals; compatibility is not an exemption.

Each Pack may publish `recognition_projection`, mapping only scope, scenario
and measure to fields in its payload. The application copies values exactly.
It rejects duplicate fields, unknown sources, missing target fields and
colliding mappings. No domain defaults or semantic mapping live in Application
or Kernel code. The Pack may publish a JSON Schema `recognition_constraints`
for the expanded goal. These constraints run before immutable acceptance and
use the existing bounded correction budget. A general intent cannot gain a
domain proposal. Existing schemas without projection still work.
