## One public tool with a discriminated schema

Keep the published name `agent_research_cycle`. Replace the permissive plan+round+assessment bundle with one operation per call. Publish a strict `oneOf`/discriminated union; each branch has `additionalProperties:false`. Use the existing SDK tool-call ID as the immutable request identity. `expected_revision` is the host research revision, not a new counter/database.

```text
plan {
  operation: "plan", expected_revision,
  goal, output_mode: "text" | "files",
  objectives: [{id, purpose, questions: [text], depends_on: [id],
                expected_outputs: [text], checks: [text]}],
  source_refs: [admitted_ref]
}

record {
  operation: "record", expected_revision, action_id,
  findings: [{id, text, status: "hypothesis" | "supported" | "refuted",
              refs: [admitted_ref]}],
  outcome: "completed" | "limited" | "failed",
  product_refs: [existing_product_ref_or_workspace_path],
  limitations: [text]
}

assess {
  operation: "assess", expected_revision, assessment_action_id,
  coverage: [{objective_id, status: "met" | "partial" | "unmet",
             refs: [admitted_ref_or_inspected_product_ref], explanation}],
  checks: [{description, status: "passed" | "failed" | "not_run",
            refs: [admitted_ref], explanation}],
  decision: "continue" | "revise" | "deliver" | "limited" | "blocked",
  summary,
  follow_ups: [{id, purpose, questions, depends_on,
                expected_outputs, checks}]
}
```

`continue` selects a ready existing objective or needs at least one follow-up. `revise` requires a concrete changed objective/method responding to a recorded discrepancy; it preserves valid findings/products. `deliver` has no new follow-ups. `limited` and `blocked` require a useful explanation and preserve saved work. Empty source refs are valid at planning time. Unsupported findings remain hypotheses. Do not demand a deterministic checker for every task or an independent evaluator model.

Use current configured capacities rather than new fixed small limits. Questions and checks are bounded planning text, not full files. Sources/products use durable versioned references; processing and model-context budgets stay separate from resource storage quotas. Read source slices on demand. The cycle must not introduce base64 file bodies.

The existing `agent_research_read` provides inspection/recovery. Existing `agent_research_update` remains available for free research notes and existing professional callers, but cannot mutate the cycle's accepted state or complete its pending action. Do not add a fourth competing state store.

## State in the existing research checkpoint

Store one versioned checkpoint through the existing research controller. Suggested payload:

```text
schema: capstone-enterprise-cycle/1
owner: {thread_id, work_id, research_id, goal_revision}
revision: existing host research_revision
phase: planning | executing | assessing | delivering | done | limited | blocked
plan: accepted goal/output_mode/objectives
round: monotonically increasing work boundary number
objectives: {id -> pending | running | executed | met | partial | failed | limited}
pending_action: {id, kind: execute|assess|deliver, objective_ids,
                 attempt_id, source_watermark, expected_outputs, checks}
findings/product_refs/limitations: bounded references and summaries
last_assessment: decision and references
```

Do not implement a second mutable revision alongside `research_revision`; the payload may omit the duplicate field. Goal revision changes create a new accepted planning revision and retain history. A new Attempt reuses Work/research identity but receives a new execution action binding. Historical receipts remain historical and cannot satisfy a new Authority evidence requirement implicitly.

Transition rules:

| Transition | Host action | Model/executor action |
| --- | --- | --- |
| planning → executing | Commit plan and activate a ready objective; return action ID and concise instructions | Do real work with the admitted tools |
| executing → assessing | Validate `record` against actual receipts/products and commit results | Submit findings and limits after meaningful work |
| assessing → executing | Commit assessment and activate a ready/follow-up objective | Resolve the identified gap |
| assessing → delivering | Commit assessed coverage and inspect required outputs | Prepare or repair the existing report/products if needed |
| delivering → done | Confirm actual inspected products/text coverage and saved required output | Produce the final user answer |
| any → limited/blocked | Preserve useful work and explicit limits | Explain what remains; no fabricated success |

An objective may include many tool calls and model responses. Split when the business purpose or method changes, a dependent result becomes available, a material discrepancy appears, or the output needs assessment. There is no tool-count threshold and no per-tool plan/evaluate tax. Initial decomposition can contain one meaningful objective when further work depends on source discovery; do not force a speculative task graph.

## Assessment and supplementation are separate actions

`record` commits an executed round and returns an assessment action with its own ID. It must not consume a pre-supplied delivery decision in the same call. The next model action evaluates the actual recorded result, relevant source slices and saved products. This can occur in the same SDK session without a separate model runtime.

Assess output coverage, material conflicts, relevant calculation checks, and report usability. Keep existing numerical checks, reproducibility files, substantive analysis and report format. File presence/hash inspection is necessary for files, but does not replace these checks. A hypothesis is allowed in research; it cannot alone satisfy an objective that requires a supported conclusion. State incomplete checks honestly; a nonessential missing check can yield a limited delivery rather than stopping unrelated work.

When a discrepancy matters, the assessment commits a targeted follow-up. Its next execution action points to the affected objective, actual conflicting refs and the product revision to repair. Run that work and then assess its result. Do not regenerate all correct calculations or rewrite a valid report from scratch. Do not add predetermined domain-specific checks to the generic reducer; the selected Pack/task supplies the applicable checks.

The host verifies shape, ownership, phase, known receipt status, product identity and explicit coverage. The model supplies analysis. Neither `assess` nor a child result is represented as independent verification unless that status is established through the owning contract.
