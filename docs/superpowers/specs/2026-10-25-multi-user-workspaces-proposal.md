# 多人使用与工作空间隔离方案

**已撤回，仅保留历史讨论。** 2026-10-25用户否决账号/成员/团队空间方案，
改为由URL的`workspace`参数命名工作空间：同名或复制URL进入同一空间，
不同名字进入不同空间；没有`thread`时显示选择/新建入口，不自动创建会话。
已有数据保留；后续再考虑工作空间选择器。本分支已实现URL隔离候选，
前后端定向测试通过；真实数据库迁移与本地重建验收尚未完成。
左栏显示实际空间名；命名空间以请求头冻结，服务端按空间过滤目录并守卫
会话资源。名称不是账号认证，知道空间名的人可共享该空间。
下文是被替代的原提案，不是当前设计、权限策略或交付计划。

## 已撤回的原提案

状态：设计提案，尚未实现，也未批准正式切换登录或数据归属。
用户要求考虑多人使用。默认推荐“个人私有空间 + 显式加入的团队空间”；
该默认组织方式仍待用户确认。当前允许的开发阶段无登录访问保持原样。

## 现状与已有边界

已核实 local-dev 的 /api/v1/thread-access 返回 mode=open。
当前服务端 Thread 目录按 archived 和创建游标查询，没有用户或成员过滤。
同一环境的访问者共用后端会话目录。浏览器 storage namespace、阅读缓存和
草稿仅分离客户端状态，不提供数据授权隔离。框架架构也明确将经过认证的
tenant/actor scope 列为未实现能力。不能把当前状态称为多人隔离已经完成。

现有资源设计中的 workspace_id 还包含会话/任务工作域语义。协作工作空间
是身份与授权边界；任务执行工作域是隔离运行边界。实施前要明确区分命名与
迁移映射，不能因为字段同名就直接复用为组织成员权限。

## 推荐对象与权限

| 对象 | 所有权与职责 |
| --- | --- |
| User | 稳定的认证身份；身份由服务端验证，不能信任浏览器自行声明的 user_id |
| Workspace | 个人或团队的数据/授权边界；一个用户可以加入多个空间 |
| Membership | 关联用户、空间和角色；最小角色为 owner、editor、viewer |
| Thread / Resource / Product | 属于一个空间；created_by 记录作者，不代替访问检查 |
| Attempt / Execution grant | 继承 Thread 的空间，记录真实发起人和执行主体；worker 不继承用户原始凭据 |
| UserThreadState | 每人的最近访问、归档/置顶偏好、切换计数和阅读状态 |

个人空间默认私有。团队空间由 owner 邀请成员；editor 可创建和执行任务，
viewer 只读。删除、导出、凭据使用等操作分别检查明确权限。共享一个 Thread
表示成员可看到同一段对话和产品，不表示共享各自的输入草稿或阅读位置。

“关闭缓存/个人归档”与“删除团队数据/关闭业务任务”必须分开。团队中一个人
收起或重新打开某会话，不应改变另一人的最近列表，也不应取消团队后台任务。
当前全局 archived 字段不能直接作为多人模式下的个人归档状态。

## 服务端强制隔离

Application / Host 负责认证、成员策略和 Workspace 选择。Kernel 接收中性的
已验证作用域与执行许可，不嵌入组织成员目录或业务权限语义。Domain Pack
仍只接收明确授权的资源引用；Authority 的模型修订、结果和证据边界保持不变。

所有入口都应从已验证身份解析有效空间，再检查成员资格：列表、按 ID 读取、
发送/取消、SSE、历史重放、上传分片、产品预览/下载和恢复。不能只在左栏过滤，
也不能靠难猜的 thread_id 或 bucket 路径防止跨空间访问。后台任务的租约、
重试、输入装配和产品入库必须保留同一空间和发起人作用域。

制品位于私有存储，以带空间身份的版本化引用访问，浏览器继续只拿有界 API
投影。GB 级资源仍使用分片、持久引用和按需读取；上传容量、处理预算和模型
上下文预算分别管理。共享空间不能隐式扩大模型、Provider 或 Authority 授权。
Provider 凭据仍由后端保护，不进入浏览器缓存、构建变量或任务工件。

同一 Thread 的多人提交继续使用现有版本/CAS、幂等回执及执行租约，不能让
两个客户端各自覆盖工作状态。多人可同时读取，冲突写入要保留明确的拒绝或
队列语义。成员退出空间后立即停止其新提交和读取；已执行工作的历史不删除。
运行中许可的撤销与安全收口需要单独的可验证合同，不能声称现有取消就已实现。

## 客户端与缓存

保留现有三栏和成熟对话组件，只增加明确的工作空间切换入口。
授权后，目录、产品和 SSE 均由当前空间过滤。切换空间或账号时先停止旧读取，
不能短暂显示另一主体的数据。登录和账号退出是正式多人阶段的单独交付。

缓存、最近列表、草稿和个人归档至少按 origin + user_id + workspace_id 隔离；
浏览器窗口/标签页可再有本地子作用域。退出登录时释放内存 DOM、blob URL 和
连接，并清理该身份的本地敏感状态；不把退出登录等同于取消后台任务。

内存会话上限采用已确认的10/20/50，缺省10。切换计数和最后打开时间属于
个人访问偏好；不能用团队其他成员的访问热度决定当前人的缓存留存。
服务端“会话最后更新”与个人“最后打开时间”是不同字段，悬浮提示不得混用。
跨空间的客户端总内存预算与切换恢复策略要在实施时明确，不能让每个空间
各自开满上限而冒充一个窗口的总上限。

## 迁移与实施顺序

1. 确认个人/团队默认方式、角色、共享粒度及当前数据归属。
2. 接入经验证的用户身份，增加 Workspace/Membership，并给 Thread、资源和
   产品建立完整作用域链；先完成服务端隔离及反例测试。
3. 增加个人 UserThreadState、团队邀请及工作空间切换，复用当前 UI 和缓存机制。
4. 验证多客户端写入、任务恢复、权限变更、产品访问和操作审计后，再开放多人试用。

既有数据保留在明确的 legacy/shared 归属下，不能自动交给第一个登录者，
不能通过新建空数据库完成所谓迁移。确认归属后执行可回滚的赋权/迁移并保存
验收记录。cloud-dev 与 demo 的账本、制品和令牌继续分离；不因多人功能合并环境。

## 验收与待决问题

验收必须包含 A/B 两用户、至少两个空间和跨 ID 访问反例。覆盖所有读写入口、
SSE 断线续接、产品下载、资源装配、个人归档不影响他人、旧缓存不能越界、
并发提交不覆盖、worker 作用域连续和原有 Authority 证据规则。

待确认：默认个人私有还是默认团队共享；首个身份提供方；团队邀请范围；
现有共享数据的负责人；运行中权限撤销策略。此提案不自动变成当前 UI 工作的
新增发布门禁，也不表示上述功能已完成。
